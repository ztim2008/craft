# Decisions

## ADR-0001 · Legacy HTML is the renderer

Puck не заменяет страницу React-компонентами. Он редактирует поля Page Model. Патчер меняет text/src в исходном DOM. CSS/JS/классы Крафтума остаются.

## ADR-0002 · Отдельный сайт, не НОРДИК

Проект живёт на `craft.nordic-builder.ru`. Конструктор nordic-builder.ru не трогаем.

## ADR-0003 · Jobs на файлах в Phase 1

Без Prisma/Postgres до доказательства crawler. JSON в `storage/jobs`. Postgres — отдельный контейнер, не `leads-pg`.

## ADR-0004 · AI не в MVP

Тип секции берём из `cli-block cli-*` и `data-type`. Не распознали → LegacySection.

## ADR-0005 · Playwright только здесь

На хабе запрещён Playwright для Profi. Этот Chromium — только миграция сайтов, headless, с SSRF-guard.

## ADR-0006 · Страницы same-origin, assets — нет

Страницы обходим только same-origin. Картинки и CSS Крафтума с Selectel/CDN скачиваем в Phase 2, иначе копия слепая.

## ADR-0007 · id узлов Крафтума

Парсер обязан понимать `id="n-…"` и `id='n-…'`. На kc3748.craftum.io атрибуты в одинарных кавычках.

## ADR-0008 · Puck позже патчера

Сначала crawler → копия → mappings → patch. В ZIP: страницы, меню, publish. Целевой UI клиента — клик по своему сайту, как в Craftum (ADR-0027). Puck/оверлей не пересобирает страницу и не блокирует первую выкладку.

## ADR-0009 · Продукт: migration + deployable admin

Не SaaS-конструктор. Free demo (1 page preview) → paid export.zip + admin на хостинге клиента. Техподдержка не в базовой цене.

## ADR-0010 · Формы: сохранить Craftum-верстку

Перехватываем submit, поля извлекаем динамически из HTML. Не заменяем форму универсальным шаблоном в MVP.

## ADR-0011 · Delivery форм

Заявка всегда в CRM-инбокс (админка клиента / leads.jsonl). Почта Craftum и «настройки формы на сайте» не маршрут. Email, Telegram, Sheets — позже, опционально. Без email заявка всё равно принимается.

## ADR-0012 · Preview asset paths

Inline CSS vars резолвятся от URL stylesheet → relative `./assets/` ломается. В HTML: absolute `/preview/{jobId}/assets/{file}`. `<base href>` для link/script.

## ADR-0013 · Admin UI

WordPress-style: sidebar, overview, content, forms, HTML blocks, publish. Один владелец, без ролей.

## ADR-0014 · HTML blocks

Разрешены style и script (owner-only). AI: OpenAI, output HTML + style tag.

## ADR-0015 · SEO в export с первого дня

В `site/` сразу: `sitemap.xml`, `robots.txt`, `canonical` в `<head>`.  
Preview использует `https://craft.nordic-builder.ru/preview/{jobId}/...`.  
На хостинге клиента host подставляется из настроек админки (title/description/OG — Phase admin).

## ADR-0016 · Sitemap.xml как источник URL

При multi-page crawl сначала читаем `/sitemap.xml` (и вложенные sitemapindex), затем добираем ссылки с страниц. Same-origin only.

## ADR-0017 · Админка сервиса Craft

Один владелец. Сессия cookie HMAC. Email/hash пароля в `.env`, не в git. Импорт и job API закрыты. Preview остаётся публичным для демо.

## ADR-0018 · Export без Next.js админки

В zip клиенту: `public/`, `data/`, `admin.html`, `patch.cjs`, `server.mjs`. Редактор страниц на хостинге клиента. Пути `/preview/{jobId}/` → `/`.

## ADR-0019 · HTML-блоки в исходный DOM

Блок вставляется before/after секции `id="n-…"`. Style и script разрешены (owner-only). Маркеры `<!--craft-block:id-->`, чтобы повторный патч не дублировал вставку. React страницу не рендерит.

## ADR-0020 · Оплата после воронки

Сначала публичное демо и заявка Basic/Pro. ZIP по токену после отметки «Оплачено» в админке. ЮKassa не в этом этапе: эквайринг не должен блокировать проверку импорта и пакета.

## ADR-0021 · Редактор в пакете клиента

В zip: `server.mjs` + `admin.html` + `patch.cjs`. Тот же DOM patch, что на Craft. Логин паролем из `.env`. Next.js в пакет не кладём. Оригинал HTML — `data/source/`, публикация пересобирает `public/`.

## ADR-0022 · Цены в админке

Basic/Pro хранятся в `storage/settings/pricing.json`, правка в `/admin/settings`. Не коммитить. Новые заявки берут актуальную сумму; уже созданные заявки не пересчитываются.

## ADR-0023 · Контур на демо-домене оператора

Финал приёмки: миграция + выкладка пакета на свой хостинг/демо-домен + проход клиентским сценарием. Это отдельный этап после кода, не смешивать с ЮKassa/AI.

## ADR-0024 · Agent API после контура

После Phase 13. Агент работает на хостинге клиента по API-ключу владельца: HTML-слоты, content overlay, publish. Не переносим сайт в React и не держим агента как наш SaaS. Оператор может тем же API дорабатывать сайты по запросу.

## ADR-0025 · Демо посетителя ≠ оплаченная миграция

Главная снимает 1 страницу и сразу открывает preview. Боевой ZIP не с воронки. В пакете: страницы и ссылки из `page-model`. Локально: static `public/` без форм; редактор — `node server.mjs`. Job демо не смешивать с job поставки клиента.

## ADR-0026 · Клиент в админке; миграция руками агента

Сущность **клиент** (имя, домен, тариф): архив и инструкция скачиваются с его карточки. Заявка с главной — лид, не карточка.

## ADR-0027 · Редактор клиента как привычка Craftum

Пакет на хостинге клиента: полотно = legacy HTML, список страниц с путями, клик по контенту и пунктам меню. Не WP-кабинет как основной UI. Puck/оверлей только мапит поля, сайт не пересобирает (ADR-0001). Хром Craftum не копируем.

## ADR-0028 · Инструкция txt и настройки пакета

Клиенту отдаём `INSTRUKTSIYA.txt` (карточка + ZIP), не markdown. В карточке: хостинг, порт, пароль `/admin` пакета, акцент инструкции на редактор. SMTP/Telegram в пакет не кладём, пока CRM-инбокс не станет привычкой.

## ADR-0029 · Patch Model поверх HTML, не page builder

Craft **не редактирует страницу**. Craft редактирует **Patch Model** поверх существующего Craftum HTML.

Страница на диске — источник правды вёрстки (классы, анимация, попапы). Редактор пишет только overlay: поля (`n-…`), секции (порядок / скрыть / удалить / вставка HTML), SEO, HTML-слоты head/body. Публикация = патч DOM. Сайт в React не пересобираем.

Это отличает Craft от Puck, GrapesJS и классических конструкторов: у них документ = дерево компонентов. У нас документ = чужой HTML, модель = список патчей. Puck не подключаем как renderer. У него можно позже заимствовать chrome (viewport, history, outline), не data model.

Секции в админке — не библиотека блоков «добавить Hero». Это управление уже снятыми `cli-block` **на канвасе** (вверх/вниз, скрыть, удалить) и вставка своего HTML во всплывающем окне. Кнопки и ссылки: текст на канвасе, **действие клика в инспекторе** (страница / якорь / внешняя / tel / mailto / файл + target/rel). Попапы Крафтума не воспроизводим. Переключатель ширины канваса (компьютер / телефон) — chrome редактора, не отдельный renderer. Новых React-секций нет.

## ADR-0030 · Слой 2: клон DOM, не новый renderer

Добавить пункт меню — клон существующего `data-type="menu-item"` (`<a class="cli-menu__link">`), новые `n-…`, вставка в каждую группу шапки (десктоп и мобильная). Overlay: `menuInserts[]` + те же действия клика, что у кнопок. Маркеры `<!--craft-menu:id:i-->`. Добавить страницу позже тем же принципом: копия HTML-каркаса + пункт меню на новый путь. Puck/библиотека блоков не подключаются.

Порядок работы над live-editor:

1. Найти все потенциально редактируемые узлы Крафтума.
2. Собрать полный Page Model (поля + секции).
3. Связка DOM ↔ model.
4. Клик по элементу.
5. Правка.
6. Сохранить patch.
7. Undo/redo — стек снимков Patch Model (не DOM). Viewport канваса. Outline секций слева. Правка текста на канвасе = тот же field patch.

Главная неизвестность на этом шаге — качество обратного анализа Крафтума, не editor UX.

## ADR-0031 · Сквозные секции: scope site vs page

В page model у секции `scope: "site" | "page"` (`src/modules/pageModel/sectionScope.ts`).

**site**, если:

- тип `header` или `footer`, или
- тип `html` и (`data-static` / `section.static`, либо тот же `n-…` на 2+ страницах).

Общие cover/text **остаются page**: иначе они исчезнут из аутлайна внутренних страниц, а отдельной вкладки у них нет.

Аутлайн страницы показывает только `page`. Шапка, подвал, сквозной HTML и меню — вкладки сверху. Правка полей с главной (тот же `n-…`) уезжает на все страницы при публикации.

Три разных «HTML» Крафтума не смешивать:

1. **Вкладка HTML-код** — блоки `cli-html` (часто CSS-виджеты кнопок, `position:fixed`). Поле `data-type="code"` → тип `html`, правка `innerHtml`.
2. **SEO / сайт** — HTML в `head` / после `body` / перед `/body`. Это настройки сайта, не секции канваса.
3. **Виджет pic** (`data-custom-class="pic"`) — часто бывший `cli-text`, **уникальный id на каждой странице**. Группируем по отпечатку (`customClass` + типы полей), overlay пишется в один `n-…`, при патче слот копируется на все страницы (`similarWidgets.ts`, ADR-0032 канвас «Виджеты»). Не смешивать с `cli-html`. `attr(class)` не должен читать `data-custom-class`.

## ADR-0032 · Канвас как Тильда: изоляция chrome

Полная страница на канвасе — только вкладки «Страница» / «Секции».  
Шапка, Меню, Подвал, HTML-код: iframe грузит ту же главную, затем `canvas.js` вешает `data-craft-focus` и класс `craft-focus-out` на чужие `section.cli-block`. Меню живёт в шапке, поэтому Меню = фокус `header`.

Не скроллить всю простыню в надежде найти подвал. Не показывать html-виджеты серыми панелями на каждой странице.

Отладка `#craft-dbg` в `admin.html` **скрыта** (мешает кликам). Логи — `console.log("[craft]", …)`. Не включать обратно без запроса.

Host → iframe: `{ source: "craft-host", focus: { mode, keepIds } }` где `mode` = `header` | `footer` | `html` | `""`.
